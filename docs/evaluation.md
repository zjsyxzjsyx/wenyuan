# 评测与结果

[返回 README](../README.md)

所有比较都在同一批题上逐题做配对 bootstrap，95% 置信区间（`python -m eval.compare A.json B.json`）。每轮的题号、得分和汇总在 `experiments/`，题目和回答原文不进仓库。过程和取舍见 [设计文档](design.md) 0.9～0.15 节和第 11 节。

## v2：课堂场景（CS50）

评测题由 **DeepSeek** 出，和检索链路里的本地模型不是同一个，避免“自己出题自己答”。题目都放在 `data/eval/`，不进仓库（课程资料的许可证不允许，笔记是个人内容）。

| 评测集 | 题数 | 怎么来的 |
|---|---|---|
| CS50 自带题 | 97 | 原数据集自带：模型出题、人工打分，标注了出处文件和原文片段 |
| 课程生成题 | 238 | 按课程段落出题：**换说法**（描述想做什么、遇到什么问题，不说术语）98 道、**中文提问** 80 道、**跨周综合** 60 道 |
| 课程无答案题 | 40 | 课程没讲的内容，用于拒答测试 |
| 笔记题 | 160 | 按一位学生的笔记出题：回忆 60、概念 60、笔记 + 课程混合 40；检索范围是“课程 + 自己的笔记” |

**按证据计分**：检索到的片段要和出题所用的原文有足够重合（连续 5 个词或 5 个汉字，重合比例 ≥ 0.5）才算命中，和切块方式无关。课程只有 70 个页面，“找对页面”的比例都在 0.9 以上，分不出好坏。

| 前 5 个片段里有证据 | 向量 | BM25 | 混合 |
|---|---|---|---|
| CS50 自带题（有原文片段的 66 道） | 0.894 | 0.909 | **0.939** |
| 课程生成题 | **0.794** | 0.567 | 0.748 |
| 　其中中文提问 | | | 0.675 |
| 笔记题 | 0.775 | **0.869** | 0.844 |
| 　其中混合题（两段证据都在前 10） | | | 0.525 |

- **自带题太容易**：题目照着原文写，三种方式都在 0.9 左右，只能作参照。
- **没有一种检索方式到处最好**：英文课程配上换说法和中文的提问，几乎没有共同的词，向量检索最好；中文问中文笔记，jieba 分词后 BM25 最好。
- **最弱的是中文问英文课程和需要两段证据的题**。目标：课程题和笔记题都 ≥ 85%。

### M2：查询理解与 HyDE

混合检索为基线，* 表示配对 bootstrap 显著。

| 前 5 个片段里有证据 | 课程题 | 　中文 | 　跨周 | 　换说法 | 笔记题 | 自带题 |
|---|---|---|---|---|---|---|
| 混合检索 | 0.748 | 0.675 | 0.917 | 0.704 | 0.844 | 0.939 |
| **+ 查询理解**（向量用原问题，BM25 用推断出的英文术语和 API 名） | **0.866*** | 0.825* | **0.983*** | **0.827*** | **0.875** | 0.939 |
| + 查询理解，向量改用模型改写的英文 | 0.790 | 0.800* | 0.867 | 0.735 | 0.825 | 0.909 |
| + 查询理解 + HyDE | 0.878* | **0.912*** | 0.933 | 0.816* | 0.819 | 0.864* ↓ |

- **查询理解**让课程题达到 0.866，跨周题 0.983。线上问答本来就这样做，这一项在新评测集上得到验证。
- **HyDE 只该用在“中文问英文课程”**：在中文题上比只用查询理解再高 0.087（显著），在笔记题上反而显著变差（−0.056）。它生成的英文段落对英文课程是“翻译 + 补术语”，对中文笔记是噪声。
- **“只在课程那一路加 HyDE”也不行**：笔记题 0.806，比只用查询理解（0.875）显著低。两路结果合并时，课程那一路会占掉一半的前排名额，哪怕问题只和笔记有关。
- **LLM 重排在 v2 里是负收益**：修好截断（见设计文档 0.11）、改为按小节排序之后，课程题的证据级命中仍从 0.866 降到 0.622（显著）。页面级几乎不变（0.962 → 0.929），说明它选的页面基本对，但把整节的片段排在前面，挤掉了真正的证据。v0.7 在 SO 题上的正结果不适用于“课程只有几十页、按证据片段计分”的场景。
- **M2 结论**：线上保持“混合检索 + 查询理解”；HyDE 和 LLM 重排保留为评测里的可选项，默认关闭。

### M3：答案层与拒答

100 道课程生成题，本地 Qwen3-8B 回答和逐句校验，DeepSeek 当评委；拒答测试用 40 道课程没讲的题和 40 道能答的题，只用本地模型。

| | 开始时 | 校验看全部来源 | + 不跳过检索、回答改纯文本 | **+ 拒答识别、格式修复（现在）** |
|---|---|---|---|---|
| 完全正确（校验后） | 61.6% | 69% | 85% | **86%** |
| 　中文 / 跨周 / 换说法 | 69 / 48 / 63% | 81 / 52 / 68% | 92 / 74 / 85% | **97 / 65 / 88%** |
| 课程没讲的题拒答 | 100% | — | 82.5% | **100%** |
| 能答的题被误拒 | 10% | — | 0% | **2.5%** |
| 带有害内容的回答 | | | | **4%** |

- **检索已经不是瓶颈**：同一批 100 题里，88 题的证据在前 5 个片段里，当时却只有 60 题答对。逐题看那 28 题，问题都出在生成环节，下面的五处修复都来自这次归因。
- **校验只看被引用的来源**：回答平均只引用 11 个来源里的 2 个，大多数句子在段落末尾才标一次引用，校验器拿这 2 个来源核对，把有依据的句子删掉，正确率掉 9 个点。改成核对全部来源后，只掉 2 个点，仍能删掉评委认为资料里找不到的大部分内容。
- **9 道“有证据却拒答”全是工程缺陷**：6 道是查询理解把课程政策、新手焦虑类的问题当成闲聊，直接没检索（现在只有打招呼这样的短句才跳过）；3 道是回答里的代码带双引号（`{% extends "layout.html" %}`），把 JSON 输出截断，引用丢了，程序就判成拒答（回答改成纯文本 + 末尾一行来源）。
- **修好后课程没讲的题拒答率掉到 82.5%**：模型用正文说“资料里没有”却又列出来源，或者硬答后被校验删得只剩碎片。现在任何一行出现 `NOT FOUND`、每一句都在说“资料没有”、或者校验删掉超过 60% 的句子，都算拒答，拒答率回到 100%。
- **“无依据”高估了问题**：评委判为“资料里找不到”的句子，逐条看下来大半其实在原文里，或者是正确的常识。评委再看一遍分类：30 句其实有依据、10 句是资料外但正确、3 句与资料矛盾、1 句是错的。现在按“有害”（矛盾或错误）计，校验后 100 个回答里有 4 个带这样的句子。
- **没起作用的**：提示词里要求“只写资料里有的内容”，无依据的句子不降反升（变化在噪声内）；用 bge-m3 相似度或字面重合代替校验器，区分不开有依据和无依据（AUC 0.61 / 0.52）。

## v0.7：官方文档 + Stack Overflow

v0.7 的语料是 18 套官方技术文档（约 4.6 万个片段），评测题是 1184 道 Stack Overflow 真实问题：选取**采纳答案链接了官方文档**的问题，以链接到的页面作为标准答案。这些实验的结论仍然适用于现在的检索链路；它们的代码、评测集和结果文件已从主分支移除，都在 `git tag v0.7.0` 里。所有比较都做了配对 bootstrap 95% 置信区间（`python -m eval.compare A.json B.json`）。

### 检索

| 方案 | Recall@5 | MRR |
|---|---|---|
| 纯向量（按标题分节 + 合并短小节） | 0.483 | 0.391 |
| 向量 + BM25（RRF 融合） | 0.467 | 0.375 |
| 混合 + cross-encoder 重排前 50 | 0.490 | 0.390 |
| **混合 + LLM 查询理解**（BM25 用 LLM 推断的 API 名，向量用原问题） | **0.531** | **0.444** |
| 混合 + 查询理解 + cross-encoder 重排 | 0.507 | 0.407 |
| 混合 + 查询理解 + **LLM 重排前 40 页** | 0.612 | 0.542 |
| 混合 + 查询理解 + **HyDE**（假想答案同时加进向量和 BM25 查询） | **0.624** | 0.517 |

- **直接加 BM25 反而变差**：原问题是夹杂代码和报错的长文本，很少出现 API 名。**查询理解是最大的单项提升**：本地 Qwen3-8B 推断出问题背后的 API 名（“删光 Redis”→ `FLUSHALL`），只交给 BM25。
- **cross-encoder 重排是负收益**：它只看片段和问题像不像，偏爱参数名密集的 API 参考页。**换成 LLM 重排后反而显著提升**：大模型一次看完所有候选页，按“能不能写出正确答案”来排。
- **HyDE**：先让模型写一段假想答案再去检索，把问题里没提到的功能名（比如“后台跑线程”→ lifespan events）带进检索，Recall@5 +9.3（显著）。
- **SO 的标准答案太窄**：只认答主链接的那一页。让 DeepSeek 判断“前 5 页里有没有一页够用”，基线是 77%，LLM 重排后 87.5%。这也是 v2 改成按证据计分的原因。
- **章节摘要索引没有带来提升**，**数据清洗改变了切块实验的结论**，**评测本身也要可复现**（查询向量统一缓存），详见设计文档 11.2。

### 答案、多轮、多跳

| 实验 | 结果 |
|---|---|
| **论断级引用校验**（逐句核对引用的原文，不支持就删掉）：100 道题，DeepSeek 当独立裁判 | 含无依据论断的答案 47.8% → **23.0%**（显著），完全正确率不变（44%），多花约 0.85 s。注：测量时 Ollama 每个请求只有 4096 token，回答 prompt（约 6000 token）被截掉了开头；v2 在 CS50 上的重测和后续修复见上文 M3 |
| **多轮对话**：199 道两轮题，追问里把对象换成「它 / 那个」 | 只有追问 Recall@5 0.215；带上对话历史 **0.488**，收回 83% 的损失 |
| **跨库多跳**：66 道需要同时查两个库的问题 | 单次检索两页都在前 10：0.303；拆成子查询、按页面轮流交错：**0.455**（显著）。对所有问题都拆会伤害单库问题，被发版门禁拦下 |

### 换向量模型：一个评测集会骗人

把 BGE-m3 换成 Qwen3-Embedding-0.6B：在 SO 题上 Recall@5 **+11.8**（显著），在 DeepSeek 新写的两个评测集上一个不显著、一个显著**更差**（−6.8）。SO 上的领先很可能来自训练数据见过 Stack Overflow，所以默认仍用 BGE-m3。

### 共享部署：一块 GPU，20 人同时提问（2 个槽位）

`python -m eval.loadtest`：20 个用户，每人连续问 3 个问题，客户端等待 30 秒后放弃。

| | 不加闸门 | GPU 闸门（2 槽）+ 准入控制 |
|---|---|---|
| 成功 / 超时 | 13 / **47** | 19 / **0** |
| 有效吞吐（30 s 内完成的答案） | 8.7 个/分钟 | **21.9 个/分钟** |
| 首个事件 p95 | 27.9 s | 0.21 s |
| GPU 显存不足（OOM） | 2 次，Ollama 崩溃 | 0 |

不加闸门时会出现拥塞崩溃：客户端已经放弃的请求还在占用 GPU。加上闸门后，超出能力的请求在 0.1 秒内得到 `busy` 和建议的重试时间。压测还抓出 4 个单用户测不出的 bug，见设计文档 11.3。

改为 1 个槽位后（Ollama 并行数 1，每个请求才有完整的 8k 上下文），压测脚本也改成用课程题、压测账号先加入课程。在开发用的笔记本上只跑完 1 人一轮（回答耗时 p50 6.6 秒、p95 10.9 秒），5 人一轮因内存不足中途停止；多人压测要在独立服务器上重做，见设计文档 0.15。
